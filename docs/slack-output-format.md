# Slack 출력 포맷 규칙 (SoT)

> **이 봇의 모든 최종 답변**(현재는 chat, 향후 잡 포함)이 따르는 단일
> 출력 규칙이다. 이 문서가 포맷의 진실의 원천(Source of Truth) — SKILL 출력 섹션·chat 시스템
> 프롬프트·egress poster 는 전부 여기를 참조한다. 값·규칙을 바꾸려면 이 문서를 고치는 PR 로만.

배경: 최종 답변은 원래 Slack **mrkdwn 평문**(`*bold*` + 불릿 나열)으로 게시돼, 표 데이터가
불릿 벽으로 뭉개지고 그룹핑이 안 보였다(사용자 지적: "보기 불편"). 이제 봇은 최종 답변을
Slack **`markdown` 블록**(GitHub-flavored markdown)으로 게시해 **표·헤더·그룹핑**을 네이티브
렌더한다.

---

## 1. 렌더 경로 (두 갈래, 같은 포맷)

최종 답변은 실행 경로에 따라 둘 중 하나로 게시되지만 **입력 포맷은 동일한 GFM** 이다:

| 경로 | 게시 방식 | 언제 |
|---|---|---|
| plan 스트림 | `chat.appendStream({ markdown_text })` → `stopStream` | 정상 경로(plan 카드가 살아 있음) |
| 폴백 poster | `chat.postMessage/update({ blocks:[{type:"markdown", text}] })` | plan 불가/죽은 스트림/재시도, 직접 게시 잡 |

두 경로 모두 Slack 이 GFM 을 네이티브 렌더하므로, 잡은 **경로를 의식하지 말고 GFM 만 잘 쓰면**
된다. mrkdwn(`*bold*`·`<url|text>`)로 쓰지 않는다 — 이제 GFM(`**bold**`·`[text](url)`)이 정답이다.

## 2. GFM 작성 규칙

> chat 은 §7 이 우선한다 — 아래 표/헤더/그룹핑 규칙은 리포트 잡 기준이다.

- **표 데이터는 파이프 표로.** 전일 대비 diff·서비스별 `error.kind` 분포·서비스별 집계처럼
  행/열이 있는 데이터는 **불릿 나열이 아니라 표**로 쓴다.
  ```
  | 서비스 | 오늘 | 어제 | 증감 |
  |---|---|---|---|
  | example-client-browser | 20 | 12 | +8 |
  ```
- **섹션은 `##`/`###` 헤더 + 빈 줄로 그룹핑.** 헤더 없이 불릿만 길게 나열하는 "불릿 벽" 금지.
- **핵심 신호를 상단에.** 🔴 블로커/급증은 **상단 요약**에 `**bold**` 로 먼저 올린다. 긴 나열은
  **상위 N개만** 보이고 나머지는 `…외 M건` 으로 접는다.
- **링크는 GFM `[텍스트](url)`.** mrkdwn `<url|텍스트>` 쓰지 않는다.
- **코드/쿼리는 인라인 `` `code` `` 또는 ```` ```블록``` ````.** 명령어·로그·쿼리 조각에만.
- **리포트 전체를 하나의 ```코드블록으로 감싸지 않는다.** 팀 규칙(SK — inline-snippet 접힘,
  `feedback_slack_no_triple_backtick_wrap`). egress 가 전체 감싸기를 자동으로 벗기지만, 애초에
  감싸지 않는 게 원칙이다.

## 3. 길이 상한 (msg_too_long 회피)

- Slack `markdown` 블록은 **≈12,000자에서 `msg_too_long` 으로 거절**된다(12,012자 실측 거절,
  2026-07-21). egress 는 안전 상한 **11,000자**(`CONTRACT.MARKDOWN_BLOCK_CHUNK_CHARS`)로 청킹한다.
- 청킹은 **섹션(빈 줄/헤더) 경계를 우선**하고, **표 행 중간·코드블록(```) 내부·`[링크](…)` 중간을
  절대 절단하지 않는다.** 표가 한 청크에 다 안 들어가면 행 경계로 나누되 각 조각에 **헤더행 +
  구분행을 재부착**해 조각마다 유효한 표가 되게 한다. (구현: `src/egress/mdBlockChunker.ts`)
- 잡 작성자는 길이를 의식할 필요 없다 — 길면 egress 가 안전하게 분할한다. 다만 **상위 N개 + 외 M건**
  규칙으로 애초에 간결하게 쓰는 것이 읽힌다.

## 4. 멘션 (`<@U…>`)

- 최종 답변의 요청자 외 `<@U…>` 멘션은 egress 멘션 게이트(`mentionGuard`)가 **평문 `@이름` 으로
  해제**해 오멘션 알림을 원천 차단한다(EG-07). 이건 mrkdwn·markdown 블록 양쪽에 동일 적용된다.
- **보수적 폴백(현행):** markdown 블록에서 허용된 `<@U>` 멘션의 렌더는 Slack 렌더러에 의존한다.
  라이브 probe 로 확정하지 못한 환경에서는 chat 최종 답변이 요청자 멘션에 의존하지 않도록
  작성한다(멘션 없이도 문맥이 성립하게). 렌더가 확인되면 이 항을 갱신한다.

## 5. 잡별 적용 요지

현재 잡은 **chat 하나**다 — 밀도 규칙이 다른 문서형 리포트와 반대이므로 §7 을 따른다.
GFM 으로 답하는 것(mrkdwn 아님)은 §2 와 같다.

두 번째 잡(리포트 성격)이 생기면 그 잡은 §2 를 그대로 따르고, 여기에 요지를 한 줄 더한다.

## 6. 짧은 상수 안내는 예외

`✅ 완료`·`⚠️ 재시도`·ACL 거부·빈 응답 안내 같은 **짧은 상수 문구**는 GFM 표/헤더가 무의미하므로
기존 `text` 경로(markdown 블록 아님)를 유지한다. markdown 블록은 **사람이 읽을 최종 답변 본문**에만.

## 7. chat 만 예외 — 대화는 문서가 아니다

리포트 성격의 잡은 §2 규칙을 그대로 따른다. **chat 잡만** 밀도 기본값이 반대다 — 대화 답변이
표·헤더로 부풀면 읽히지 않는다.

chat 최종 답변의 상한(정본은 `src/jobs/chat/styleLint.ts` 의 상수다 — 이 표는 사본):

| 규칙 | 상한 |
|---|---|
| 전체 길이(코드블록 포함) | 1,500자 |
| 한 목록의 최상위 항목 수 | 5개 |
| 불릿 한 줄의 표시 길이 | 80자 |
| 불릿 깊이 | 2단계 |
| 파이프 표 | 데이터 4행 이상일 때만 |

집행은 두 층이다. 프롬프트(`OUTPUT_FORMAT_GUIDE`)가 지시하고, `lintChatStyle` 이 게시 직전에
검사해 위반이면 같은 세션에서 재작성 1회를 돌린다. 재작성 후에도 위반이면 **그대로 게시한다** —
스타일은 취향 게이트이고 배달을 막지 않는다.

"과정 서사"(답보다 시도 과정이 긴 것)는 린트가 잡지 못한다 — 프롬프트의 ✗/✓ 예시가 전담한다.
